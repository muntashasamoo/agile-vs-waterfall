How it was run
Experiment design

The feature: a full user authentication module — registration, login, JWT token handling, and password reset. Each method received the same requirements doc at the start.

Sprint breakdown
3 sprints · 1 week each · retrospective after each
Sprint 1 — Core auth (3.5 days)
Registration endpoint, bcrypt hashing, basic JWT issuance. Sprint review revealed UX issue — email validation too strict.
Sprint 2 — Login & token refresh (4 days)
Login logic, refresh token rotation, middleware guards. Switched from HS256 to RS256 signing — caught in retro, zero rework cost.
Sprint 3 — Password reset & polish (4 days)
Email reset flow, rate limiting, integration tests. Deployed to staging at sprint end. Total: 11.5 days.
Waterfall phases
5 sequential phases — each gate-checked before proceeding
Phase 1 — Requirements (2.5 days)
Full spec document: 14-page PRD with all edge cases. Signed off before any design work.
Phase 2 — System design (3 days)
Architecture diagrams, DB schema, API contract. Mid-design: realized HS256 inadequate — had to revise PRD (+0.5 days).
Phase 3 — Implementation (5 days)
Coding against frozen spec. Two spec ambiguities discovered — resolved by re-reading PRD, not by testing.
Phase 4 — Testing (4 days)
9 defects found — 3 traced to requirement gaps. Rework sent implementation back. Costly.
Phase 5 — Deployment (3 days)
Integration issues with staging environment. Total: 18 days.

Key Findings
What this experiment revealed

Six concrete conclusions drawn from 18 days of parallel development — applicable to individual developers and small teams.

⚡

Speed advantage is real

Agile completed the feature 36% faster. Most savings came from reduced documentation overhead and earlier defect detection.

🐛

Defect cost compounds

Waterfall bugs found in Testing cost ~5× more to fix than Agile bugs caught during sprint review. Late discovery means more rework.

🔄

Change tolerance is decisive

When the JWT signing algorithm changed mid-project, Agile absorbed it in one retro. Waterfall required partial re-entry of the Design phase.

📋

Waterfall excels in clarity

The 14-page PRD forced thorough upfront thinking. For regulated or safety-critical systems, this traceability is genuinely valuable.

🎯

Solo developers benefit less

Agile's collaboration ceremonies (standup, retro) felt over-engineered alone. A trimmed personal version — weekly review + kanban — was more practical.

📈

Motivation tracks delivery

Deploying working code at each sprint end created momentum. Waterfall felt flat until the very end — nothing to "ship" for 15 days.

Conclusion

Agile wins for web feature development — with conditions

For a solo developer building a standard web feature with evolving requirements, Agile reduces total time by ~36%, cuts rework by ~80%, and improves adaptability at every phase. Waterfall remains the right choice when requirements are truly immutable or regulatory traceability is mandatory. For this course project context: Agile is the clear recommendation.
